D) PAYMENT CHECKOUT FLOW
------------------------------------------------------------

Payment should happen AFTER creator accepts booking.

Booking lifecycle:
1. Driver requests booking
2. Creator accepts
3. Booking status becomes payment_pending
4. Driver pays
5. Webhook marks transaction paid and booking paid/in_progress
6. Creator delivers footage
7. Driver approves/completes booking

Add API endpoint:

POST /api/bookings/:bookingId/create-checkout-session

Behavior:
- Auth required.
- Only assigned driver can create checkout session.
- Booking must be accepted or payment_pending.
- Creator must have stripeAccountId and charges enabled.
- Server calculates all amounts:
  - package price snapshot
  - platform fee
  - creator payout
- Create Stripe Checkout Session in payment mode.
- Use destination charge:
  - payment_intent_data.application_fee_amount = platformFeeAmount
  - payment_intent_data.transfer_data.destination = creatorStripeAccountId
- Add metadata:
  - bookingId
  - transactionId
  - driverId
  - creatorId
  - eventId
- Save stripeCheckoutSessionId and paymentStatus=pending.
- Return checkout URL.

Client UI:
- Booking Detail shows “Pay Now” only for assigned driver when status is payment_pending.
- Pressing “Pay Now” opens Stripe Checkout URL.
- After return, app should refresh booking detail.
- Do not mark paid from client return URL; wait for webhook.

------------------------------------------------------------
E) STRIPE WEBHOOKS
------------------------------------------------------------

Add endpoint:

POST /api/stripe/webhook

Requirements:
- Use raw body parsing for this route.
- Verify Stripe signature with STRIPE_WEBHOOK_SECRET.
- If signature invalid, reject request.
- Webhook is source of truth.

Handle events:
1. checkout.session.completed
   - Find transaction by stripeCheckoutSessionId or metadata.transactionId.
   - Store stripePaymentIntentId.
   - Mark paymentStatus=paid.
   - Update booking status=paid or in_progress.

2. payment_intent.succeeded
   - Confirm paid state if metadata matches booking/transaction.

3. payment_intent.payment_failed
   - Mark paymentStatus=failed.
   - Booking remains payment_pending.

4. charge.refunded
   - Mark refunded or partially_refunded.

5. charge.dispute.created
   - Mark paymentStatus=disputed.
   - Booking status=disputed.

6. account.updated
   - If event is for connected account, update user Stripe status:
     - charges_enabled
     - payouts_enabled
     - details_submitted

Important:
- Stripe recommends webhooks for post-payment events, not trusting redirect/callback alone.
- Add idempotency protection so duplicate webhook events do not double-update records.
- Store received Stripe event IDs if needed.
